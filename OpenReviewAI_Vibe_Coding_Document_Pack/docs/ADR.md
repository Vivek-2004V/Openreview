## ADR-001: Local CLI First; Defer Hosted SaaS

- **Status:** Accepted
- **Context:** Developers need immediate, private code reviews without cloud subscriptions, data privacy concerns, or recurring infrastructure costs. Building a multi-tenant cloud service introduces complex IAM, webhook queues, billing, and secret management before core review efficacy is proven.
- **Decision:** Build OpenReview AI as a standalone local CLI tool first. Defer multi-tenant SaaS, web portals, and database microservices until local review precision and developer value are proven.
- **Consequences:**
  - Positive: Fast feedback loop, zero cloud infrastructure cost, 100% data privacy by default.
  - Negative: Team-level aggregated dashboards and background GitHub App webhooks are deferred to later milestones (Phase 7+).

## ADR-002: Explicit Origin Separation (`static`, `ai`, `combined`)

- **Status:** Accepted
- **Context:** Developers distrust AI code reviews when tools hallucinate line numbers, invent CVEs, or present speculative opinions as verified facts.
- **Decision:** Every finding in `Finding` schema v1 must declare its origin explicitly:
  - `static`: Purely deterministic tool findings (e.g. Ruff, ESLint, Bandit) backed by tool rule IDs, exact line ranges, and raw tool output.
  - `ai`: Heuristic or contextual suggestions generated by a local LLM. Must be explicitly flagged as unverified suggestions.
  - `combined`: A deterministic finding enriched or clarified with local AI explanation.
- **Consequences:**
  - Positive: High trust and explainability; zero confusion between compiler/linter errors and AI hypotheses.
  - Negative: Requires deduplication and origin merging logic when combining scanner and AI observations.

## ADR-003: Versioned Schema Validation for All Outputs

- **Status:** Accepted
- **Context:** Integrations (CI pipelines, IDE plugins, JSON consumers) break if output formats change arbitrarily between releases.
- **Decision:** All review reports must strictly validate against versioned schemas (`Finding` schema v1, `ReviewReport` schema v1). Both Markdown (for human reading) and JSON (for machine consumption) must derive from the identical validated report model.
- **Consequences:**
  - Positive: Predictable contract for CI/CD exit codes and future UI adapters.
  - Negative: Any change to report structure requires formal schema version bumping (`v1.1`, `v2.0`).

## ADR-004: Untrusted Input & Zero Model-Driven Command Execution

- **Status:** Accepted
- **Context:** Prompt injection in source code, README files, or commit messages can instruct an LLM to execute shell commands, read environment secrets, or alter system files.
- **Decision:**
  - Treat all repository text, diffs, comments, and model outputs as **untrusted data**.
  - The model provider interface (`ModelProvider`) can only return structured suggestion data. It cannot trigger subcommands, invoke shell interpreters, or modify files.
  - All external tool executions must use allowlisted subprocess argument arrays (e.g., `["git", "diff", ...]`) with explicit timeouts, without `shell=True`.
- **Consequences:**
  - Positive: Immune to prompt-injection-driven remote code execution on the developer's machine.
  - Negative: The model cannot automatically run arbitrary ad-hoc fix scripts.

---

## ADR-005: Human Approval Required for All Patches and Merges

- **Status:** Accepted
- **Context:** Automated bot commits and merges can introduce subtle regressions, security bugs, or formatting thrashing on default branches.
- **Decision:** OpenReview AI will never automatically commit, merge, or alter the repository's default branch. Suggested fixes are presented as unified diff proposals and can only be applied in a disposable scratch worktree after explicit human review and approval.
- **Consequences:**
  - Positive: Prevents repository corruption and maintains human-in-the-loop governance.
  - Negative: Requires manual developer action to apply proposed changes.

---

## ADR-006: REA Decoupling & Optional Investigation Role

- **Status:** Accepted
- **Context:** REA is an agent-oriented reverse engineering framework designed for binary disassembly (Hopper, Ghidra, IDA) and web observation. It does not provide source code review or linter orchestration.
- **Decision:** OpenReview AI maintains **zero runtime coupling** to REA. OpenReview AI is built as a clean, lightweight Python package. REA remains an optional developer/investigation tool if binary artifact verification is needed in future releases.
- **Consequences:**
  - Positive: Lightweight distribution, fast install (<1s), no heavy binary/Java/native addon dependencies.
  - Negative: None for source code review.
